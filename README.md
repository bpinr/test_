# 🐾 Go Pet Shop

**Go Pet Shop** — это учебный проект интернет-магазина товаров для питомцев, написанный на Go с использованием PostgreSQL.  
Он создан для отработки навыков работы с SQL-запросами, транзакциями и построения REST API.

---

## 🚀 Основная идея

Проект моделирует классический онлайн-магазин с товарами, пользователями, заказами и оплатами.  
Цель — показать полный цикл разработки от работы с базой данных и CRUD-операций до реализации транзакций и аналитики.

---

## 🔑 Возможности проекта

- 📦 Управление товарами (добавление, обновление, удаление, просмотр списка и конкретного товара).  
- 👤 Работа с пользователями (регистрация, получение списка и конкретного пользователя).  
- 🛒 Создание заказов и добавление позиций.  
- 💳 Оформление заказов в транзакции (уменьшение остатков, создание заказа, позиций и транзакции оплаты).  
- 📊 Просмотр истории заказов и аналитики (популярные товары, детали заказов и транзакций).  
- ✅ Health-check для проверки состояния сервера.

---

## ⚙️ Технологии

## 🛠 Как запустить

1. Клонировать репозиторий:
   `git clone https://github.com/bpinr/test_.git`
   `cd test_`

2. Настроить окружение: скопировать `.env.example` в `.env` и поправить логин, пароль и имя базы.
`cp .env.example .env`

3. Поднять PostgreSQL и применить миграции:
`docker compose up -d postgres`
`task migrate`

4. Запустить сервер (конфиг `config/local.yaml`, другой выбирается через `APP_ENV`):
`go run ./cmd/app`

5. После этого API будет доступно по адресу:
`http://localhost:8080`, проверка — `GET /health`.

Всё сразу в контейнерах: `docker compose up -d --build` (приложение берёт `config/dev.yaml`).

## 🧪 Тесты HTTP-хендлеров

Unit-тесты хендлеров `/products` лежат в `internal/handlers/product/products_test.go`.
Базу данных в них подменяет мок интерфейса `Products`, поэтому PostgreSQL для тестов не нужен.

Каждый хендлер (`GetAllProducts`, `CreateProduct`, `UpdateProduct`, `DeleteProduct`) покрыт сценариями:
успех (200), битый вход (400, кроме `GetAllProducts`) и ошибка хранилища (500).
Битый вход: некорректный JSON для `CreateProduct` и `UpdateProduct`, пустой id для `DeleteProduct`,
нечисловой id (`abc`) для `UpdateProduct` и `DeleteProduct`.
В каждом тесте проверяются и HTTP-статус, и тело ответа.

### Ветки `tests-manual` и `tests-mockery`

| | `tests-manual` | `tests-mockery` |
|---|---|---|
| Мок | `internal/handlers/product/product_mock.go`, написан руками | `internal/handlers/product/mocks/Products.go`, генерирует mockery |
| Поведение задаётся | полями-функциями: `CreateProductFunc: func(...) {...}` | ожиданиями: `m.On("CreateProduct", ...).Return(42, nil)` |
| Новый метод в интерфейсе | дописать метод в мок руками | перезапустить `go generate ./...` |
| Проверка вызовов | вручную, через переменные в замыкании | автоматически: `mocks.NewProducts(t)` сам вызывает `AssertExpectations` в конце теста |

Логика тестов в обеих ветках одинаковая, отличается только способ создания мока.

### Как запустить тесты

```bash
go test ./...
```

Подробный вывод по каждому тесту: `go test ./internal/handlers/product/ -v`.

### Как перегенерировать моки (ветка `tests-mockery`)

Над интерфейсом `Products` в `internal/handlers/product/products.go` стоит директива:

```go
//go:generate go run github.com/vektra/mockery/v2@v2.53.7 --name=Products
```

Перегенерировать мок после изменения интерфейса:

```bash
go generate ./...
```

Mockery устанавливать отдельно не нужно, `go run` скачает нужную версию сам.

### Линтер

```bash
task linter
```
